### util/ArtworkCache.kt
- **[MED] `trimToCap` runs a full directory scan on EVERY write.** `ArtworkCache.kt:57,83-94`.
  - Reasoning: each `write()` ends with `dir.listFiles()` + `sumOf { it.length() }` — an O(N) stat sweep (N = cached covers, up to ~250-400 at the 256 MB cap). The enricher/favourite sweep writes covers in bursts (DriveTagEnricher.kt:244,287), so a burst of W writes costs O(W×N) file stats on Dispatchers.IO. Not user-visible today (N is hundreds, stats are µs-ms), but it is quadratic churn and pure waste when total ≤ cap (the common case still pays the full listFiles+sum).
  - Change candidate: early-exit counter (trim every Nth write) or maintain an approximate running total (AtomicLong seeded lazily). Interdependence: cap enforcement is the #3 audit fix for unbounded cover growth; LastPlayedScreen/PlaybackService read via `uriFor` and tolerate eviction.
  - Preservation: (a) safe if the cap is still enforced eventually (throttled trim keeps the invariant, only with bounded overshoot ≈ N writes × 1 MB); (b) defends prior bug: unbounded coverart growth (header comment "#3 — cover art was unbounded"); (c) recurrence prevented because the trim itself is kept — only its frequency changes. The atomic temp-then-rename write and the SHA-256 key are **KEEP-DO-NOT-TOUCH** (both are explicit prior-bug fixes: torn-file race and 32-bit hash collisions, documented at lines 21-22, 40-55).
- [MED] Eviction is FIFO-by-write, not LRU: `uriFor` reads never bump `lastModified`, so `trimToCap`'s oldest-by-lastModified order evicts the most-displayed cover as readily as a never-viewed one. `ArtworkCache.kt:62-65,88`. Candidate: `f.setLastModified(now)` on `uriFor` hit (one syscall per read; cheap) — makes the documented "LRU" claim true. Preservation: (a) safe — only changes eviction ORDER under pressure; (b) defends nothing that changes; (c) N/A. Interdependence: the 256 MB cap raise (lines 67-73) was partly compensating for this mis-eviction during browses — true LRU makes a future cap REDUCTION plausible (storage win), but do not lower the cap in the same change (the comment documents re-download churn as the failure mode).
- [LOW] `write()` on the same-size skip path still calls `trimToCap` (`ArtworkCache.kt:42-57`) — a no-op write pays the full O(N) scan. Folds into the throttling candidate above.
- [INFO] SHA-256 per key on `uriFor`/`write`: hashing a short URI string is ~µs — NOT a hot-path cost. KEEP (collision defence is documented and load-bearing: DB bakes in the path).
- [MED] `ArtworkCache.uriFor` called during composition — `ui/lastplayed/LastPlayedScreen.kt:868-870` wraps it in `remember(item.mediaUri)`, but the first composition of every row does SHA-256 + `File.exists()` (disk stat) on the main thread. Dozens of rows → dozens of main-thread stats on first paint of Last Played. Candidate: resolve in the ViewModel (it already owns the item list) or `produceState`. Preservation: (a) safe — same value, different thread; (b) defends prior bug: the durable-cover-over-dangling-artworkUri preference (comment lines 862-866) MUST keep its priority order, only the lookup thread moves; (c) recurrence guarded by the existing comment travelling with the moved code.
