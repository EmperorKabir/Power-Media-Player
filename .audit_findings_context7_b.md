## 1. Media3 1.6.0 (`/androidx/media`)

### 1.1 [LOW] PlaybackService.kt:379-387 — deprecated `COMMAND_SET_DEVICE_VOLUME` reference (the known warning)
- Doc (api.txt, /androidx/media): `setDeviceVolume(int)` and `setDeviceMuted(boolean)` are `@Deprecated`; the `VolumeFlags` overloads replace them. `COMMAND_SET_DEVICE_VOLUME_WITH_FLAGS` was added in 1.1.0 (RELEASENOTES 2023-07-05).
- Code reality: the actual mutator call is the **two-arg, non-deprecated** `p.setDeviceVolume(target, 0)` at :387. The deprecation warning at :380 arises solely from referencing the deprecated *constant* `Player.COMMAND_SET_DEVICE_VOLUME` inside a defensive availability check that accepts either the new or legacy command.
- Reasoning: usage is doc-correct where it matters (the setter). The legacy-constant check is defensive compatibility: a `Player` implementation (remote controller, older wrapper) may advertise only the legacy command; dropping the check could silently disable the cast fade on such players.
- Interdependence: this is the CASTFADE sleep-timer fade path — device-verified behaviour (remediation 2026-06-27). CastSession path (:370-376) is primary; CastPlayer path is already the fallback.
- PRESERVATION: **KEEP-DO-NOT-TOUCH** the dual check. Cosmetic option only: `@Suppress("DEPRECATION")` on the enclosing function to silence the compile warning. (a) suppression is a zero-behaviour change; (b) the dual check defends against players advertising only the legacy command — removing it risks a silent fade no-op; (c) with suppression the warning goes away without touching logic, so no recurrence path.

### 1.2 [MED] audio/AudioDelayProcessor.kt — missing `onFlush()`; ring buffer survives seek/flush
- Doc (BaseAudioProcessor.java source via Context7): `BaseAudioProcessor` "handles configuration/flush/reset state management. Subclasses override … `onFlush()` for state resets." The base `flush()` clears only the *output* buffer; any subclass-held buffered PCM must be dropped by the subclass in `onFlush()`.
- Code reality: `AudioDelayProcessor` holds up to 2000 ms of PCM in `ring` (`writePos`/`readPos`/`filled`, :40-46) and overrides **no** `onFlush`/`onReset` (grep over `audio/*.kt`: Equalizer :201/:209, Reverb :187/:192, VoiceBoost :110 and HueAnalyserAudioProcessor :197 all override `onFlush`; AudioDelayProcessor does not; Gain and StereoTransform are stateless so correctly need none).
- Consequence: with a non-zero A/V delay configured, a seek (which flushes the sink) leaves pre-seek audio in the ring; the first post-seek output emits up to `delayMs` of stale audio from the old position — audible glitch, worst on BT-video-offset users (the processor's whole audience).
- Interdependence: only active when `btVideoAudioOffsetMs > 0` and PCM16 (onConfigure gate :54); pass-through path (:79-84) drains `filled` first, so the stale tail also leaks out of delay→0 transitions after a seek.
- PRESERVATION pre-annotation (change candidate: add `override fun onFlush() { writePos = 0; readPos = 0; filled = 0 }`):
  - (a) Safe: flush happens exactly when ExoPlayer discards its own buffered audio (seek, format change, stop); dropping ring content then matches what every sibling processor in this codebase already does.
  - (b) Prior-bug defence: none identified — vc29.26/vc29.27 comments cover allocation reuse, not flush semantics; the scratch-buffer reset lives in `onConfigure` and is untouched.
  - (c) No recurrence: resetting the three indices reproduces the exact post-`onConfigure` state (:62), which is already proven-good.

### 1.3 [VERIFIED-CORRECT] BaseAudioProcessor buffer-ownership contract across audio/ + hue/
- Doc: `replaceOutputBuffer(size)` returns the internal (reused, direct, native-order) buffer; caller must write then `flip()`; one output buffer per processor — calling it twice per `queueInput` would clobber output.
- Verified: every processor (`AudioDelayProcessor`, `EqualizerAudioProcessor`:156-168, `GainAudioProcessor`:38-55, `ReverbAudioProcessor`:96-127, `StereoTransformProcessor`:52-61, `VoiceBoostAudioProcessor`:76-86, `HueAnalyserAudioProcessor`) calls `replaceOutputBuffer` at most once per `queueInput`, fully consumes the input buffer, and flips. `replaceOutputBuffer(0).flip()` during delay warm-up (:107) is legal (empty output, input consumed). `onConfigure` returning `AudioFormat.NOT_SET` for non-PCM16 (:54) is the documented deactivation idiom.

  - (b) Prior-bug defence of current usage: possible deliberate battery choice for a mostly-local library; no in-code comment claims that, but this project's rules demand evidence before player changes (no-guesswork policy) — no user-reported screen-off-stall symptom is on file.

  - Verdict: legitimate candidate but **evidence-gated** — only apply if a screen-off network-stall symptom is ever logged; otherwise KEEP.

## 3. DataStore preferences 1.1.7 (`/websites/developer_android_topic`)

### 3.1 [LOW-MED / KEEP-DO-NOT-TOUCH] The single ~127-key "settings" store (data/preferences/SettingsDataStore.kt:13)
- Doc: the binding rules are (i) exactly one DataStore instance per file per process (top-level `by preferencesDataStore(name = "settings")` — complied, single delegate, singleton `SettingsDataStore` via Hilt); (ii) `edit`/`updateData` is transactional. Docs impose **no key-count limit** and give no store-splitting mandate; the practical costs are whole-file rewrite per edit and one cold parse.
- Observed costs are already known and mitigated in-code: cold reads 300-500 ms under load (PlaybackService.kt:1298-1329 comment), bounded `runBlocking + withTimeoutOrNull(200/600)` seeds with defaults-on-miss.
- Why KEEP: splitting the store would require a key-migration and would re-tune the cold-start timing that the 600 ms seed window was *specifically enlarged for* (the "half-second un-pitched audio" tester bug). The current single-store + bounded-seed design is a defence against that prior bug; a split could shift latencies in either direction and reintroduce it. No doc-backed gain justifies that risk.
- Sub-note [INFO]: the `runBlocking` seeds are a documented anti-pattern in general but are deliberate, bounded, StrictMode-acknowledged (PowerMediaPlayerApp.kt:67-76 penaltyLog-only comment names them). Doc-conformant compromise.

## 4. WorkManager 2.10.0 (`/websites/developer_android_topic`)

### 4.1 [HIGH] podcast/PodcastSyncWorker.kt:141-145 — `ExistingPeriodicWorkPolicy.KEEP` + constraints changed across releases under an unchanged unique name → stale constraints persist on upgraded installs
- Doc (workmanager/how-to/managing-work): "`KEEP` (ignores new work)" — if unfinished unique periodic work exists, the new request (including its Constraints) is discarded. `UPDATE` (added 2.8) exists precisely to replace the spec of existing periodic work while preserving its enqueue time and period.
- Evidence chain:
  - `UNIQUE_NAME = "podcast_sync_periodic_v1"` (:127) has never changed since introduction (git: only 88239d8 touches the string).
  - Constraints DID change: 50c19a6 "fix(podcast): Wi-Fi-only auto-sync" set UNMETERED; the current code sets `NetworkType.CONNECTED` per the explicit user directive of 2026-06-26 (comment at :134-138); fc3fb29 (M5 download gate) also reshaped download behaviour.
  - `enqueueIfNeeded` runs every process start (PowerMediaPlayerApp.kt:127-129) but with KEEP it is a permanent no-op on any install that enqueued under the old spec. No `cancelUniqueWork` exists anywhere (grep: zero hits).
- Consequence: every install that ran a Wi-Fi-only build keeps the UNMETERED constraint forever → periodic podcast sync silently never runs on mobile data, directly contradicting the shipped 2026-06-26 behaviour. Fresh installs behave correctly — which is why device tests on a clean install would not catch it.
- PRESERVATION pre-annotation (change candidate: `ExistingPeriodicWorkPolicy.UPDATE`):
  - (a) Safe: UPDATE is the doc-designed mechanism for exactly this; it preserves the period start/next-run time, so calling it on every app start does not reset or thunder the schedule; when the spec is identical it is effectively idempotent.
  - (b) What KEEP defended against: re-enqueue churn from `enqueueIfNeeded` firing every onCreate. UPDATE retains that protection (no schedule reset), so the defence carries over.
  - (c) Recurrence: with UPDATE, all future constraint/interval edits propagate automatically; the class of bug is eliminated, not patched. Double-safety: mobile-data spend is independently gated *inside* the worker (`downloadsAllowed` + MobileDataPolicy), so widening the run-constraint cannot cause unwanted downloads.

## 10. Platform APIs (targetSdk 35) (`/websites/developer_android`)

### 10.1 [HIGH] alarm/BootCompletedReceiver.kt:30-50 + AndroidManifest.xml:263-272 — Direct Boot: `LOCKED_BOOT_COMPLETED` handler reads credential-encrypted DataStore → crash before first unlock
- Doc: `directBootAware` components run before user unlock and may access **only device-protected storage**; credential-encrypted (default) app storage is unavailable until unlock. The receiver is `directBootAware="true"` and registered for `LOCKED_BOOT_COMPLETED`, but its handler's first act is `settingsDataStore.scheduledAlarms.first()` — a read of `filesDir`-backed (CE) Preferences DataStore.
- Failure path: at locked boot the DataStore file open throws; the exception propagates out of `first()` inside a `try { … } finally { pendingResult.finish() }` — **no catch** — into a `CoroutineScope(SupervisorJob() + Dispatchers.Default)` with no `CoroutineExceptionHandler` → uncaught → process crash on every reboot of a Direct-Boot device. Alarms are still re-armed later by the second delivery (`BOOT_COMPLETED`, post-unlock), so the feature partially self-heals — which hides the crash from casual testing.
- Second-order defect: the *purpose* of handling `LOCKED_BOOT_COMPLETED` (ring even if the user never unlocked after an overnight reboot) is not achieved, because the alarm records live in CE storage.
- PRESERVATION pre-annotation (two-tier change candidate):
  - Tier 1 (minimal, unambiguously safe): wrap the body in `runCatching` (keep `finally { finish() }`). (a) Cannot regress anything — it converts a crash into the exact same no-op the crash produced, and BOOT_COMPLETED still re-arms; (b) current code defends nothing — the try/finally exists only to finish the async receiver; (c) recurrence prevented for the crash class.
  - Tier 2 (full fix, larger): persist `scheduledAlarms` in `context.createDeviceProtectedStorageContext()`-backed storage so pre-unlock re-arm actually works. This moves data between encryption domains — needs a one-time migration and a deliberate decision that alarm times are OK in device-protected storage (they are non-sensitive; the platform's own AlarmClock apps do this). Do not attempt casually; Tier 1 first.
- Interdependence: `AlarmScheduler.schedule` itself (setAlarmClock + PendingIntent) needs no storage and would work pre-unlock; only the read blocks.

### 10.2 [MED — manifest pattern + Play policy] AndroidManifest.xml:49-50 — both `SCHEDULE_EXACT_ALARM` and `USE_EXACT_ALARM` declared unbounded
- Doc (Manifest.permission reference): "only one of `USE_EXACT_ALARM` or `SCHEDULE_EXACT_ALARM` should be requested on a device. If your app … needs `USE_EXACT_ALARM` on SDK 33+, then `SCHEDULE_EXACT_ALARM` should be declared with a max-sdk attribute": `<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM" android:maxSdkVersion="32" />`. The in-code comment (AlarmScheduler.kt:14-16) already understands this split but the manifest doesn't implement it.
- Play-policy note (same doc): USE_EXACT_ALARM is auditable; intended for apps where exact alarms are **core** functionality (alarm-clock class). A media player with a wake-up-alarm feature is defensible (it IS an alarm clock feature ringing media) but should have a prepared justification for Play review. Also note the side effect: holders of USE_EXACT_ALARM are pinned to the WORKING_SET standby bucket or lower — a real (documented) battery/standby cost of keeping this permission.
- PRESERVATION pre-annotation (change candidate: add `android:maxSdkVersion="32"` to SCHEDULE_EXACT_ALARM):
  - (a) Safe: this is the doc-verbatim pattern; on API 30-32 SCHEDULE_EXACT_ALARM continues to apply (min SDK 30), on 33+ USE_EXACT_ALARM auto-grants — every supported API level keeps a valid exact-alarm path; `setAlarmClock` (AlarmScheduler.kt:37,75) is the correct doc-recommended API for user-visible alarms and needs no change.
  - (b) What the double declaration defends: nothing beyond belt-and-braces; the system resolves precedence anyway. No prior bug attached.
  - (c) Recurrence: n/a — declarative.
