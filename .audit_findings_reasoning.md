## components/CoverArtBackground.kt
[HIGH] Side effects (Diag logging + `onColorsExtracted(null)`) executed in the composition body — runs on every recomposition, not per event.
CoverArtBackground.kt:114-117 (`Diag.i("PMP_DIAG", "CoverArt AsyncImage building uri=$artworkUri")`) and :163-168 (else-branch `Diag.i(...); onColorsExtracted(null)`). Every such recomposition: (1) builds the interpolated log String (allocation) and, if diag enabled, does log I/O; (2) in the no-art branch, invokes `onColorsExtracted(null)` — a state-writing callback — DURING composition, which violates Compose's side-effect rules (composition may be abandoned/reapplied) and fires repeatedly.
Practical impact is capped by two things: PlayerScreen isolates position ticks into a separate PositionUi flow (PlayerUiState.kt:139 doc), so the parent shouldn't recompose per frame; and MutableState writes of an equal value don't invalidate. Interdependence: the null-clear is part of the stale-album-art fix chain (memory note "Album art — two root causes", RESOLVED 2026-06-14): when a track has no art, downstream palette-tinted UI must reset. Moving it to LaunchedEffect delays the clear by one frame — acceptable (colors drive tint, not layout), but the clear MUST still fire on every transition into the no-art state.
Preservation: (a) safe if the LaunchedEffect keys cover exactly the branch condition; (b) the code defends against stale palette colours persisting onto art-less tracks (documented bug, fixed 2026-06-14); (c) the defence is preserved — only the mechanism moves from composition-body to effect; the condition (track change to no-art) still triggers it. The two Diag.i composition-body logs themselves defend nothing (pure diagnostics) — removable freely; the onError/onSuccess/skip logs inside callbacks can stay.

## components/CoverFrost.kt
[HIGH] Luminance sampling does a full-cover GPU readback + full-size software copy per sample, per text line.
`rememberResolvedTextColour` (:154-179): on every (frost.captured, bounds, palette) key change it calls `frost.sharp.toImageBitmap()` — a synchronous GPU→CPU readback of the WHOLE captured cover layer — **on the Main thread** (only `averageLuminance` is moved to Dispatchers.Default). Then `averageLuminance` (:109-137) finds the layer bitmap is HARDWARE config and does `src.copy(ARGB_8888)` — for a full-screen cover on this phone (1080×2520) that is a ~10.9 MB transient allocation — to then read ≤121 sampled pixels. Every FrostedTextLine (title + artist + album + description = up to 4 on the audio layout) runs its OWN rememberResolvedTextColour, so one track change ≈ 4 × (Main-thread GPU readback + ~10 MB copy + sample loop). GC pressure spike + Main-thread stall exactly at track-change time (which is also when the decode/palette work runs).
Worse: `bounds` (a Rect from onGloballyPositioned, FrostedTextLine :240) is a key — during any layout animation or controls-overlay shift, bounds changes per frame → per-frame full-bitmap readback+copy. This is the sort of drain the objective targets.
Fix shape (ranked): (1) crop-first — `GraphicsLayer.toImageBitmap()` has no region parameter, but the copy can be avoided by drawing the layer region into a small ARGB_8888 Bitmap via Canvas (record → software canvas draw of just the bounds rect, ~a few KB); (2) share one readback per frame across all FrostedTextLines (hoist sampling to the frost object keyed by a sample epoch); (3) debounce bounds (e.g. snapshotFlow + collectLatest with a 50-100 ms settle) so animations don't thrash; (4) move `toImageBitmap()` off Main if API allows (it must run where the layer is readable — verify; if Main-bound, the small-region draw makes the Main cost tiny).
Interdependence: THE delicate geometry contract — the pill frost draws `translate(coverOrigin - origin) { drawLayer(f.blurred) }` (:261) and the text colour must match the sampled region behind THAT pill. Sharing one sample across lines is safe only for lines whose regions have similar luminance — sampling per line exists precisely because title and artist sit over different cover regions. So fix (1)+(3) are safe; fix (2) would change per-line colour decisions and must sample per-line regions from ONE readback (readback shared, sampling per line) — that preserves behaviour exactly.
Preservation: (a) region-copy + shared-readback + debounce keep identical outputs (same pixels sampled); (b) the key set (captured, bounds, palette) is a documented stale-luminance regression fix (:164-167 comment: keying on captured alone kept a stale decision across cover changes with same-width titles) — the KEYS MUST NOT be reduced; (c) the fix does not touch keys, only the per-fire cost. The `copy(ARGB_8888)` itself defends against HARDWARE-config getPixel crashes — the small-region software draw replaces it while keeping software-readability guaranteed.

[MED] `captureCoverFrost` re-records BOTH GraphicsLayers on every draw pass of the cover (:101-106): `sharp.record{...}` + `blurred.record{ drawLayer(sharp) }` + a state write `frost.captured = true` inside draw. Cover redraws are rare when static (good), but every invalidation (fold, resize, palette-driven overlay, entering/leaving video) re-records the blur chain. The `captured = true` write in a draw phase is same-value after the first frame (no invalidation loop — Compose skips equal writes), so it's benign but should ideally be conditional (`if (!frost.captured)`) to avoid the snapshot-write machinery per draw. LOW-cost tweak, no behaviour change.
Preservation: capture-in-draw is the core of the "read what was truly drawn" design (robust to Fit/Crop/zoom/fold — file header :57-66); do NOT replace with source-bitmap sampling — that was the rejected "transform guess" approach.

[LOW] FrostedTextLine drawBehind allocates a `Path()` per visual line per draw (:254). Draw only re-runs on invalidation (layout/text/frost changes), not per frame, so cost is modest; could be cached keyed on line metrics, but the cache invalidation complexity outweighs the win. KEEP as-is.
[LOW] Double Text composition (stroke pass + fill pass, :300-318) doubles glyph layout/draw for every frosted line. This is the standard Compose outline technique; a single Text with drawStyle can't do fill+stroke together. KEEP — legibility feature, documented (2026-06-30 user issue).

## app/src/main/java/com/powermediaplayer/ui/settings/SettingsViewModel.kt

### [HIGH] 78-flow indexed combine: 78 live DataStore collectors, 78 map stages, full rebuild per write
- File: SettingsViewModel.kt:168-344 (`uiState` combine over `listOf<Flow<Any>>(…78 flows…)`).
- Reasoning:
  - The list has 78 entries (indices v[0]..v[77]), not 77 — `downloadFilesOnMobileData` is v[77].
  - Each entry is (per the standard SettingsDataStore pattern) a separate `dataStore.data.map { prefs -> … }` flow. Preferences DataStore emits the WHOLE `Preferences` snapshot to every downstream collector on EVERY write. So one toggle write = 78 upstream emissions → 78 `map` lambda executions → 78 array-slot updates in `combine`'s internal machinery → 1 full 78-field `SettingsUiState` allocation + 78 casts + a structural `equals` against the previous value (which itself walks 78 fields incl. a `Set<String>` and a `List<AlarmRecord>`).
  - `combine(List<Flow<Any>>)` also boxes every primitive (Boolean/Int/Float → objects) into an `Array<Any>` per emission — GC churn during slider bursts.
  - Cost is bounded by `SharingStarted.WhileSubscribed(5000)`: hot only while some screen collects `uiState`. But `uiState` is not Settings-only — it carries player-facing fields (videoControlsHideSec, artworkScaleMode, pitch, crossfade…), so if any player/overlay composable collects this VM's `uiState`, the 78-collector web stays hot during PLAYBACK, which is the battery-relevant window. (Cross-check for lens 2/3: grep collectors of `SettingsViewModel.uiState` outside SettingsScreen.)
  - Cheaper alternative preserving exact semantics: ONE flow — `settingsDataStore.data.map { prefs -> SettingsUiState(prefs[K1] ?: d1, …) }.distinctUntilChanged()`. One collector, one map, zero boxing arrays, no index bookkeeping, and type-safe (no `as` casts). Requires SettingsDataStore to expose either raw `data` or a prebuilt `settingsUiStateFlow`. Second-best: split `uiState` into per-section state objects so only the visible section's flow is hot (the codebase is ALREADY migrating this way — see AutoplaySettingsUi, btMappingSet, voiceBoost, fontSizeScaleFlow comments "kept separate to avoid index churn").
- Interdependence: every settings row reads `uiState.<field>`; changing the combine's shape touches SettingsScreen's ~60 field reads. Any consumer outside SettingsScreen (player auto-hide timers etc.) also re-keys. The index-based `v[n] as T` mapping means ANY insertion mid-list silently shifts types — a latent runtime-ClassCastException trap the single-map alternative eliminates.
- Preservation: (a) safe because the replacement is semantically identical (same fields, same defaults, same distinct semantics); (b) the current shape is itself a regression-guard accretion — comments vc29.26 and "Audit 2.5" document past fixes (theme unsubscribed from the big combine; distinctUntilChanged+conflate added for slider bursts); those fixes' INTENT (fewer hot collectors, no duplicate emissions) is strengthened, not weakened, by the single-map form; (c) the prior bug (theme recomposing on any write) cannot recur since the theme reads `fontSizeScaleFlow`/`themeAccentHexFlow`, which are untouched. Verdict: SAFE-TO-CHANGE but only as a deliberate refactor with the full settings matrix re-tested; NOT a mechanical deletion.

### [LOW] `.distinctUntilChanged().conflate()` before `stateIn` are no-ops
- File: SettingsViewModel.kt:338-344.
- Reasoning: `stateIn` produces a StateFlow, which already (1) conflates (latest-value semantics) and (2) skips value-equal emissions. Both operators therefore duplicate StateFlow's built-in behaviour, each adding a channel/operator hop (an extra coroutine buffer stage for `conflate`). Still, the vc29.26 comment is a regression-guard marker: if removed, keep the comment explaining StateFlow provides the same guarantee. Micro-win only; fine to KEEP if churn risk outweighs it.

## service/PlaybackService.kt (3975 lines)

### [MED] B4-PS-1 — WAKE_MODE_LOCAL under-locks network sources
- PlaybackService.kt:1273 — `setWakeMode(C.WAKE_MODE_LOCAL)` holds only a partial wakelock, no WifiLock. The app streams Drive (`https://googleapis.com`) and podcast HTTP sources through this same player; on screen-off long streams, Wi-Fi doze can stall buffering.
- Reasoning: Media3 `WAKE_MODE_NETWORK` adds a WifiLock; unconditional NETWORK raises battery on local playback (the common case). `ExoPlayer.setWakeMode` is runtime-mutable — the correct minimal change is to flip mode per current item scheme (http/https → NETWORK, else LOCAL) from the existing onMediaItemTransition listener.
- Interdependence: none of the crossfade/cast machinery reads wake mode. Cast playback bypasses local wake needs entirely (CastPlayer).
- Preservation: (a) safe — pure additive switch, LOCAL retained for local files; (b) no prior-bug comment on this line; (c) a stall regression can't recur since LOCAL remains the default. CHANGE-CANDIDATE.

### [MED] B4-PS-2 — subtitleDelayMs collector re-prepares per slider tick (no debounce)
