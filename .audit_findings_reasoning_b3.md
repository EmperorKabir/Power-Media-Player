## lastplayed/LastPlayedScreen.kt

### [HIGH] B3-LP1 — SwipeToDismiss saved-state can resurrect a row in "dismissed" pose after Undo
- Location: `LastPlayedScreen.kt:344-360` (recents `SwipeToDismissRow` + vc31 Undo) and `SwipeToDismissRow` at 603-639.
- Reasoning: `rememberSwipeToDismissBoxState` persists via `rememberSaveable` inside the LazyGrid's saveable-state holder, keyed by the item key `"dyn_${it.id}"`. The vc31 Undo path deliberately restores the SAME history id (`undoDeleteRecentsRow` → "ids preserved", `LastPlayedViewModel.kt:272-277`). Sequence: swipe → state settles at `EndToStart` → row leaves composition (LazyGrid RETAINS saveable state for departed keys) → Undo re-inserts identical key → the restored row can rehydrate the dismissed anchor state and render fully swiped (background delete icon only, content translated off-screen). No key/state reset exists between delete and restore.
- Interdependence: depends on `LastPlayedViewModel.lastDeletedRecent` id-preserving restore (a correctness feature for bookmarks); also on Material3 SwipeToDismissBoxState's Saver behaviour — needs one device verification (swipe-delete → Undo → inspect row).
- Preservation: fix candidate = reset path only (e.g. `key(item.id, restoreGeneration)` wrapper or non-saveable state). (a) Safe: visual state only, no data change. (b) Prior bug defended: the id-preserving restore fixed bookmark loss — DO NOT change ids; fix the swipe state instead. (c) Recur-proof: a generation counter bumps only on undo. Until verified on device: KEEP-DO-NOT-TOUCH data path, flag UI-state fix only.

### [MED] B3-LP2 — Resume-live pinned rows hold one Room subscription each; table-wide invalidation fan-out
- Location: `HistoryHeaderRow` 834-838 (`livePositionProvider` → `repo.observePositionFor(uri)` → Room flow on `playback_history`).
- Reasoning: not a timer — it is Room-invalidation-driven, so battery cost is bounded; but EVERY write to playback_history (the periodic position persist during playback, recordPlay, deletes) invalidates ALL Resume-live pin queries (≤10) → up to 10 re-queries + row recompositions per persist tick while playing. Bounded and intentional (#19 live display). Micro-optimisation: `distinctUntilChanged()` on the flow before collect would suppress equal-value recompositions.
- Interdependence: #19 feature contract ("updates as you play"). Preservation: adding distinctUntilChanged is (a) safe — same values; (b) defends nothing lost; (c) n/a. Low urgency.

### [MED] B3-LP3 — `ArtworkCache.uriFor` disk probe in composition
- Location: 867-870, `remember(item.mediaUri) { ArtworkCache.uriFor(ctx, item.mediaUri) }`.
- Reasoning: if `uriFor` touches the filesystem (File.exists), it runs on Main once per row-first-composition — ~20 rows on first scroll = ~20 stat() calls. Minor jank risk on slow storage. Candidate: resolve in VM mapping. Preservation: (a) safe move, same value; (b) durable-cover-first logic defends the dangling-cache-path bug (comments 862-866) — keep the PRIORITY ORDER byte-identical; (c) covered by comment contract.

### [MED] B3-LP4 — PinnedAlbumRow collects member-track flow while collapsed

## podcast/PodcastsSection.kt

### [HIGH] B3-P1 — Un-remembered Flow creation in composition: `EpisodeList` + `EpisodeRow` re-subscribe Room on recomposition
- Location: `EpisodeList` line 749 — `vm.episodesFor(feedUrl).collectAsStateWithLifecycle(...)`; `EpisodeRow` line 773 — `vm.episodePosition(e.audioUrl).collectAsStateWithLifecycle(initialValue = null)`.

These two are the only violators in the batch.

- Interdependence: none behavioural — subscription hygiene only; the derived played/in-progress logic (779-783) is untouched.
- Preservation: fix = `remember(feedUrl) { vm.episodesFor(feedUrl) }` / `remember(e.audioUrl) { vm.episodePosition(e.audioUrl) }`. (a) Safe — identical data, stable subscription; (b) prior bug defended: none — the bogus-itunes:duration guard (778-780) is unrelated and untouched; (c) recurrence prevented by matching the established remember(id) convention. APPLY-SAFE.
