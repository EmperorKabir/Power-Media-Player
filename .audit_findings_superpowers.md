# ANDROID DEEP AUDIT — Lens 3 (Superpowers structured-review methodology) — Part A: UI half

Scope: `app/src/main/java/com/powermediaplayer/ui/` — 66 files, ~1.4 MB.
Batches: P1 player core (PlayerScreen/PlayerViewModel/PlayerUiState) · P2 player/components + ui/components · P3 cloud (CloudBrowserScreen/CloudViewModel) · P4 settings (13 files) · P5 library + lastplayed + smartplaylists · P6 podcast + info + navigation + equalizer + downloads + overrides + theme + stats + adaptive.

Methodology applied per component:
1. **VERIFICATION-BEFORE-COMPLETION** — claimed behaviours (comments, `git log --oneline -- <path>`, TASKS.md) verified against delivered code; claim/code mismatches flagged with evidence.
2. **SYSTEMATIC-DEBUGGING** — failure-mode enumeration (nulls, races, lifecycle, cancellation, config change on the foldable, process death) with concrete failure scenarios for unhandled modes.
3. **PLANNING** — implementation-shape vs problem-shape mismatches (duplicated state machines, hand-synchronised parallel paths) with quantified sync burden.

Objective: code minimisation (footprint, speed, battery, memory, CPU, storage, store acceptance). Every finding carries INTERDEPENDENCE; every removal/change candidate carries PRESERVATION PRE-ANNOTATION ((a) why safe, (b) prior bug defended against per `git log -S` / regression comments, (c) why it cannot recur) or is marked KEEP-DO-NOT-TOUCH.

Status: sections appended incrementally as each batch completes. A batch summary table closes the file.

- REFUTED as per-visual-line-per-frame: the per-line pills in FrostedTextLine (CoverFrost.kt:241-291) are pure GPU work — clipPath + drawLayer(f.blurred) + dim rect inside drawBehind. A single track change (palette key changes) therefore triggers 5 full-layer readbacks on the main thread plus up to 5 HARDWARE-to-ARGB_8888 software copies (CoverFrost.kt:112) on Default — ~55 MB transient allocation and 5 GPU stalls per track change.

Safe minimisation that keeps the defence: (a) sample ONCE per (captured, palette, coverOrigin) into the shared CoverFrost holder (one readback), then derive each line's regional luminance from that single software bitmap keyed by each line's bounds — behaviour identical, readbacks drop 5x to 1x; additionally debounce bounds (snapshotFlow + debounce) so animations sample once at rest. (b) Prior bug defended: illegible text over high-contrast covers + stale colour across track change — both preserved because sampling still uses the real captured layer and still re-keys on palette. (c) Regression cannot recur if the single shared sample keeps the same keys (captured, palette, bounds-at-rest). Anything beyond that (e.g. replacing readback with palette-only guessing) is KEEP-DO-NOT-TOUCH — that is exactly the bug this design exists to kill.

### [HIGH] B-13 `directBootAware` receiver + LOCKED_BOOT_COMPLETED reads CE-encrypted DataStore — REFINES lens2's HIGH: silent no-op re-arm (probable) or crash (device-dependent); either way the Direct-Boot wiring is wrong

- Methodology: DEBUG (process-death/boot-stage failure modes) + VERIFY of lens2's claim.
- Reasoning, exact chain at locked-boot stage on an FBE device (all minSdk-30 devices):
  1. LOCKED_BOOT_COMPLETED fires → the process starts in Direct Boot mode → `PowerMediaPlayerApp.onCreate` runs first. `DiagLog.init` touches `getExternalFilesDir` (null before unlock → falls back to CE `filesDir`, whose `mkdirs()` fails silently — File APIs don't throw). `appScope.launch { settingsDataStore.diagLogEnabled.collect … }` (line 97-99) opens the Preferences DataStore, whose file lives in CE storage.
  2. `BootCompletedReceiver.onReceive` then does `settingsDataStore.scheduledAlarms.first()` (line 36) against the same CE-backed DataStore.
  3. Outcome depends on how the kernel surfaces the unavailable CE dir: ENOENT → DataStore's FileNotFound path emits `emptyPreferences()` → `alarms` = empty → **zero alarms re-armed, logged as success** ("Boot reschedule: 0 alarm(s)"); EACCES/other IOException → the read flow THROWS → uncaught in `scope.launch` (BootCompletedReceiver has no CoroutineExceptionHandler; the `finally` finishes the broadcast but the exception still propagates to the default handler) → process crash at every boot. Neither outcome is the designed behaviour.
  4. Mitigation that saves the FEATURE: `BOOT_COMPLETED` fires again after unlock, the receiver runs a second time with CE available, and alarms re-arm then. - The manifest comment (lines 258-262) claims LOCKED_BOOT_COMPLETED support "so no alarm silently dies" — claim NOT delivered: without moving `scheduledAlarms` to device-protected storage (`context.createDeviceProtectedStorageContext()`-backed DataStore), the locked-stage pass cannot read anything.
- Interdependence: PowerMediaPlayerApp's own locked-stage behaviour (StrictMode, WorkManager enqueue on a background thread wrapped in runCatching at line 127-129, the A4 `noBackupFilesDir` guard at 122) is individually guarded, but every @HiltAndroidApp graph member constructed at locked boot must be CE-safe — today nothing else is exercised, which is why this hasn't visibly burned.
- Preservation pre-annotation — TWO legal fixes, pick ONE:
  - Fix-A (minimal, recommended): drop `directBootAware` + the LOCKED_BOOT_COMPLETED action. (a) Safe: BOOT_COMPLETED still re-arms after unlock — the status quo for the overwhelming majority of alarm apps; (b) prior bug defended: the three-action set was belt-and-braces from §C12, no incident behind the locked variant (git shows it landed with the feature, not as a fix); (c) recurrence n/a — removing the locked path removes its failure mode.
