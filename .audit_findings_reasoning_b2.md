## app/src/main/java/com/powermediaplayer/ui/settings/SettingsViewModel.kt

### [HIGH] 78-flow indexed combine: 78 live DataStore collectors, 78 map stages, full rebuild per write
- File: SettingsViewModel.kt:168-344 (`uiState` combine over `listOf<Flow<Any>>(…78 flows…)`).
- Reasoning:
  - The list has 78 entries (indices v[0]..v[77]), not 77 — `downloadFilesOnMobileData` is v[77].
  - Each entry is (per the standard SettingsDataStore pattern) a separate `dataStore.data.map { prefs -> … }` flow. Preferences DataStore emits the WHOLE `Preferences` snapshot to every downstream collector on EVERY write. So one toggle write = 78 upstream emissions → 78 `map` lambda executions → 78 array-slot updates in `combine`'s internal machinery → 1 full 78-field `SettingsUiState` allocation + 78 casts + a structural `equals` against the previous value (which itself walks 78 fields incl. a `Set<String>` and a `List<AlarmRecord>`).
  - `combine(List<Flow<Any>>)` also boxes every primitive (Boolean/Int/Float → objects) into an `Array<Any>` per emission — GC churn during slider bursts.
  - Cost is bounded by `SharingStarted.WhileSubscribed(5000)`: hot only while some screen collects `uiState`. But `uiState` is not Settings-only — it carries player-facing fields (videoControlsHideSec, artworkScaleMode, pitch, crossfade…), so if any player/overlay composable collects this VM's `uiState`, the 78-collector web stays hot during PLAYBACK, which is the battery-relevant window. (Cross-check for lens 2/3: grep collectors of `SettingsViewModel.uiState` outside SettingsScreen.)
  - Cheaper alternative preserving exact semantics: ONE flow — `settingsDataStore.data.map { prefs -> SettingsUiState(prefs[K1] ?: d1, …) }.distinctUntilChanged()`. One collector, one map, zero boxing arrays, no index bookkeeping, and type-safe (no `as` casts). Requires SettingsDataStore to expose either raw `data` or a prebuilt `settingsUiStateFlow`. Second-best: split `uiState` into per-section state objects so only the visible section's flow is hot (the codebase is ALREADY migrating this way — see AutoplaySettingsUi, btMappingSet, voiceBoost, fontSizeScaleFlow comments "kept separate to avoid index churn").
- Interdependence: every settings row reads `uiState.<field>`; changing the combine's shape touches SettingsScreen's ~60 field reads. Any consumer outside SettingsScreen (player auto-hide timers etc.) also re-keys. The index-based `v[n] as T` mapping means ANY insertion mid-list silently shifts types — a latent runtime-ClassCastException trap the single-map alternative eliminates.
- Preservation: (a) safe because the replacement is semantically identical (same fields, same defaults, same distinct semantics); (b) the current shape is itself a regression-guard accretion — comments vc29.26 and "Audit 2.5" document past fixes (theme unsubscribed from the big combine; distinctUntilChanged+conflate added for slider bursts); those fixes' INTENT (fewer hot collectors, no duplicate emissions) is strengthened, not weakened, by the single-map form; (c) the prior bug (theme recomposing on any write) cannot recur since the theme reads `fontSizeScaleFlow`/`themeAccentHexFlow`, which are untouched. Verdict: SAFE-TO-CHANGE but only as a deliberate refactor with the full settings matrix re-tested; NOT a mechanical deletion.

### [LOW] `.distinctUntilChanged().conflate()` before `stateIn` are no-ops
- File: SettingsViewModel.kt:338-344.
- Reasoning: `stateIn` produces a StateFlow, which already (1) conflates (latest-value semantics) and (2) skips value-equal emissions. Both operators therefore duplicate StateFlow's built-in behaviour, each adding a channel/operator hop (an extra coroutine buffer stage for `conflate`). They do NOT reduce upstream recompute — the 78-field rebuild happens regardless.
- Interdependence: none — downstream observers see identical emissions either way.
- Preservation: (a) removal is behaviour-neutral by kotlinx.coroutines contract (StateFlow docs: "Values are conflated… equal values are skipped"); (b) added in vc29.26 to fix real slider-burst redraws — plausibly the flow was NOT a StateFlow at that time, or the fix predated understanding that stateIn dedupes; (c) cannot regress because StateFlow's conflation is a documented invariant, not incidental. Still, the vc29.26 comment is a regression-guard marker: if removed, keep the comment explaining StateFlow provides the same guarantee. Micro-win only; fine to KEEP if churn risk outweighs it.

### [HIGH] `enrichedCovers` map runs `File.exists()` per file-backed row on every table invalidation
- File: CloudViewModel.kt:129-145.
- Reasoning: the map body does `Uri.parse(url).path?.let { java.io.File(it).exists() }` for every covered row (favourites grow unbounded) on every Room invalidation of the enrichment table. During a peek sweep that's O(rows²) stat() calls in aggregate. `flowOn(Dispatchers.IO)` correctly moves it off-main, and `conflate()` (comment: "a peek storm emits fast; only the latest map matters") bounds concurrent work to one map at a time — the design is deliberate and documented. Remaining cost: stat() syscalls per emission are still linear in library size; a small memo (path → (mtimeChecked, alive)) or checking existence only for rows whose URL changed since the previous map would make it O(changed). Also note: `conflate()` here IS meaningful (unlike SettingsViewModel's) because the expensive map runs upstream of stateIn — but conflate placed AFTER `.map` does not skip map executions, only downstream delivery; to actually skip intermediate maps the conflate must be BEFORE the map (`.conflate().map{…}` on the Room flow — Room flows already conflate internally, so in practice back-pressure does elide some, but the operator as placed buys little). [Correction-grade detail for the cross-exam pass.]
- Interdependence: the exists() filter is load-bearing — it is what makes LRU-evicted `file:` art fall back to the icon and triggers sweep re-enrichment (comment lines 126-128, and sweep's `fileGone` logic mirrors it at 706-710). Any memoisation must invalidate when ArtworkCache evicts (eviction happens out-of-band, so a TTL memo of seconds, or re-stat only on stateIn subscription, is the safe shape).
- Preservation: (a) memoisation with short TTL preserves the dangling-row-renders-icon contract within one browse session; (b) prior bug: dangling file:// art after ArtworkCache LRU eviction rendered broken covers — the exists() check IS the fix (per the doc comment); do NOT remove it; (c) eviction can always recur, so the check must stay in some form. Optimise, never delete.

## app/src/main/java/com/powermediaplayer/ui/cloud/CloudBrowserScreen.kt

### [HIGH→ASSESSED-ACCEPTABLE] Per-row `LaunchedEffect(item.id) { peekCoverIfNeeded(item) }` — the mandated assessment
- File: CloudBrowserScreen.kt:699-701 (search results branch) and 1078-1080 (browse branch).
- Reasoning (recomposition cost): each grid row entering composition allocates one LaunchedEffect node + one coroutine launch. Keyed on `item.id`, so a row recomposing WITHOUT identity change does NOT relaunch; scrolling away disposes, scrolling back relaunches. Relaunch cost is bounded: `peekCoverIfNeeded` runs 6 synchronous O(1) gates (folder/provider/SAF/video/enrichedCovers-map/peekAttempted-set) before any I/O coroutine; after the first attempt the `peekAttempted` companion set short-circuits at gate 6 with zero I/O. Net: fast fling over 100 rows ≈ 100 short-lived coroutines whose bodies hit a HashSet and return — microseconds each; not a jank source.
- Reasoning (battery/network): the expensive tail is triple-bounded — Semaphore(2) concurrency, once-per-item-per-process attempt set, and a PERSISTED verdict (cover URI or NO_ART) that makes future sessions zero-network. Metered gate defers to Wi-Fi. This is close to the minimum-energy shape for viewport-driven fetching.
- Why per-row beats the alternatives: a list-level `LaunchedEffect(uiState.items)` would peek EVERY item in the folder (including never-seen rows) — strictly worse for network/battery on big folders. A snapshotFlow over visible indices would dedupe relaunches slightly better but adds complexity for negligible gain given the O(1) gates.
- Interdependence: depends on `enrichedCovers` staying available synchronously (`.value` gate) — see the CloudViewModel Eagerly finding; if that flow is demoted to WhileSubscribed the gate degrades gracefully (falls through to the DAO check inside the coroutine).
- Preservation: KEEP-DO-NOT-TOUCH. Fresh, review-hardened pipeline (I1-I5 evidence-graded verdicts); the guards ARE the prior-bug defence (peek storms / re-fetch loops). No change proposed.
