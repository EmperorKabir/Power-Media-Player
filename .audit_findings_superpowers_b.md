## Component: service/CastRelayServer.kt (+ PlaybackService cast region 2550-3250)

### [HIGH] B-1 FaststartDrive moov heads accumulate in the relay item map for the whole cast session — VERIFIES lens1 HIGH
- File: `app/src/main/java/com/powermediaplayer/service/CastRelayServer.kt:50,87,100-107,110-112`; consumer `service/PlaybackService.kt:3149-3208,3030-3037`.
- Methodology: DEBUG (resource-growth failure mode) + VERIFY of lens1's claim.
- Reasoning, fully traced:
  - `register()` (CastRelayServer.kt:100) only ever ADDS to `items` (ConcurrentHashMap). `clear()` exists (line 110) but **no call site anywhere in the repo invokes it** — grep over `service/` shows only `items.clear()` inside the class itself. The map is emptied solely by dropping the whole server object in `PlaybackService.stopCastRelay()` (PlaybackService.kt:3030-3037), which runs only on switch-back-to-local / session end.
  - Each `RelayItem.FaststartDrive` holds `head: FaststartHead` = `ftyp + patched moov` ByteArray, capped at `MAX_FASTSTART_MOOV = 48 MB` (line 60), typical ~19 MB per the T302 comment.
  - During ONE cast session, every track change while casting re-registers items: `rebuildForCast` (PlaybackService.kt:3193) is called per item on `switchPlayer` AND per item added via `onAddMediaItems` while casting (PlaybackService.kt:3686 `val relay = if (isCasting) castRelayServer else null`). Every relayed cover art also registers a (tiny) `Local` item (buildCastMetadata, PlaybackService.kt:3084).
  - Concrete failure scenario: folder-as-audiobook queue of 20 moov-at-end `.m4a` files cast to a speaker → 20 `FaststartDrive` registrations, each `prepareFaststart` fetching and RETAINING its 2-48 MB head → 40 MB-1 GB heap held until the user stops casting. On a 3-4 GB-RAM device with a 4K-video-capable heap already loaded, this is an OOM/LMK vector mid-cast. Even the single-audiobook case retains the previous book's ~19 MB head after skipping to the next book.
- Interdependence: heads are what make later seeks instant (`serveFaststart` comment line 273 "later seeks hit the cached head"); any eviction must keep the CURRENT item's head. Interacts with lens1's same finding — CONFIRMED, and with the `faststart` disk cache (separate, filesDir) which does have LRU eviction (PlaybackService.kt:2986-2995) — the in-RAM map is the only unbounded tier.
- Preservation pre-annotation for the fix candidate (evict non-current heads on item transition, or cap the map to N=2 FaststartDrive entries):
  - (a) Safe because `serveFaststart` already has a complete fallback: head==null after `ready` → `serveDrive` passthrough (line 276-279); an evicted head degrades to passthrough, never to failure.
  - (b) Prior bug defended against: T302 "cast Drive audiobook freezes because receiver fetches a 1.4 GB tail to seek" — the head cache IS the fix; deleting the mechanism outright would regress T302.
  - (c) Cannot recur if eviction only targets items other than `CastPlayer.currentMediaItem`'s token and the map keeps the newest registration.

### [HIGH] B-7 AudioDelayProcessor has NO `onFlush()`/`onReset()` — stale ring buffer bleeds pre-seek audio; tail truncated at EOS — VERIFIES cross-lens claim
- File: `audio/AudioDelayProcessor.kt:40-51` (state fields), whole class (no onFlush/onReset/onQueueEndOfStream override).

User seeks; Media3 flushes the chain; BaseAudioProcessor clears its output buffer but subclass state (`ring`, `readPos`, `writePos`, `filled`) survives.   - Concrete failure scenario 2 (track change, same format): same mechanism — last track's final 1.5 s plays at the head of the next track. Only a FORMAT change (rate/channels) resets state via `onConfigure` (lines 53-67).

- Preservation: (a) zeroing indices on flush is exactly what the other four processors do — proven pattern in this codebase; (b) prior-bug scan: vc29.26/27 comments in this file concern scratch-buffer ALLOCATION reuse only, not flush semantics — no regression-fix protects the current no-op flush; (c) recurrence impossible once the unit test asserts flush-resets-state.

### [HIGH] B-9 138 per-key `.data.map{}` flows, ZERO `distinctUntilChanged` — every write fans out to every live collector — VERIFIES lens1-B5 HIGH, with corrected fix-shape

- Reasoning:

- Preservation: (a) `distinctUntilChanged` on a `Flow<T>` of data-class/primitive values is semantics-preserving for state consumers; (b) prior bug defended against: the 77-slot positional combine off-by-one — the per-key-flow architecture IS the defence and is retained untouched; (c) recurrence: helper function makes dedup the default for every future key.

- Reasoning, exact chain at locked-boot stage on an FBE device (all minSdk-30 devices):

- Preservation: (a) format output identical; (b) no prior bug depends on the shared instances; (c) immutability removes the class of race. Pairs naturally with B-15 (same lines).
