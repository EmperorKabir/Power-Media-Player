## data/db/dao/PodcastDao.kt

### [HIGH] B5-01 — `podcast_episodes` has NO index on `feedUrl` or `audioUrl`; every hot query is a full table scan
- File: `app/src/main/java/com/powermediaplayer/data/db/dao/PodcastDao.kt:45-57,105-116` + entity `PodcastShowEntity.kt:28-43` + `AppDatabase.kt:395-407` (v10 CREATE TABLE has no indices; no later migration adds any).
- Reasoning: `podcast_episodes` is keyed by `guid` (PK) only. Hot queries that filter on non-PK columns:
  - `observeEpisodes(feedUrl)` / `episodesForFeedOrdered(feedUrl)` — the episodes list UI + auto-advance queue; `WHERE feedUrl = ? ORDER BY publishedAt DESC LIMIT 200` → full scan + sort of the whole episodes table on every Room invalidation (any episode write from any feed re-runs it).
  - `episodeByAudioUrl(url)` — called by `MediaOverrideRepository.activeOverride` on EVERY track change (`flatMapLatest` over `currentOverrideKeyFlow`, MediaOverrideRepository.kt:74-76). The comment there claims "one **indexed** suspend query per track change" — that claim is FALSE for the current schema: `audioUrl` is not indexed, so every track change does a full scan of podcast_episodes. Same for `downloadedByAudioUrl` (cold-start resume, Recents tap).
  - `audioUrlsForFeed`, `deleteEpisodesForFeed`, `downloadedForFeed` — unsubscribe/retention paths, also scans.
- Scale: with e.g. 10 subscriptions × 200 kept episodes = 2 000 rows the scan is milliseconds — not user-visible today, but it runs on the *track-change* hot path and re-runs `observeEpisodes` on every 6-hourly sync upsert batch. Cheap, pure-win fix: additive migration `CREATE INDEX index_podcast_episodes_feedUrl ON podcast_episodes(feedUrl, publishedAt)` + `CREATE INDEX index_podcast_episodes_audioUrl ON podcast_episodes(audioUrl)` and matching `indices=[...]` on the entity.
- Interdependence: MediaOverrideRepository (this batch), PodcastSyncWorker (this batch), podcast UI VMs (other batch). Adding an index changes no query results, only the plan. Requires DB version bump → coordinate with any other schema change from the audit so there is ONE migration.
- Preservation: (a) additive index only — no data or query-shape change; (b) defends nothing that could regress — prior bugs in this area (REPLACE upsert wiping download columns) live in `syncEpisodes`, untouched; (c) index cannot alter merge semantics. CHANGE-SAFE.

### [MED] B5-02 — `syncEpisodes` is an N+1 read loop inside a transaction
- File: `PodcastDao.kt:72-84`.
- Reasoning: for each parsed episode it issues `getEpisode(e.guid)` — one SELECT per episode. A 200-episode feed × N shows on every 6 h sync = hundreds of point SELECTs (PK-indexed, so each is cheap, but statement overhead × 200 × shows × 4/day adds up in CPU/battery). One `SELECT * FROM podcast_episodes WHERE guid IN (:guids)` (chunked ≤ 999 binds) + in-memory map keeps identical semantics.
- Interdependence: RssFeedParser output size (caps at what the feed carries — 1 MB feeds can carry 500+ items, see B5-24), PodcastSyncWorker cadence.
- Preservation: (a) same merged result, same @Transaction envelope; (b) THIS method is itself the regression fix — the doc comment records that a blanket REPLACE upsert used to reset `isPlayed` and wipe `localPath/localBytes/downloadedAt`, orphaning downloaded files. Any rewrite MUST keep the carry-forward of those 4 fields for existing guids; (c) recurrence prevented by keeping the copy() carry-forward exactly and adding a unit test asserting downloaded fields survive a re-sync. CHANGE-SAFE only with that invariant test; otherwise KEEP.

## data/db/entity/* + AppDatabase.kt (v21 index migration)

### [MED] B5-03 — v21 "search" indices cannot serve the LIKE '%needle%' queries they were built for; they are pure write/storage overhead
- Files: `PlaybackHistoryEntity.kt:19` (title, subtitle indices), `OfflineCopyEntity.kt:13` (displayName), `EnrichmentCacheEntity.kt:13` (title), `AppDatabase.kt:252-259` (MIGRATION_20_21).
- Reasoning: SQLite B-tree indices only accelerate `LIKE` when the pattern has a literal prefix (`'abc%'`) AND case-insensitivity conditions hold. The #16 search queries (`searchDriveMetadata`, `searchDisplayName`, `searchEnriched`) all use `LIKE :pattern ESCAPE '\'` where the pattern is (verified in DriveMetadataSearch.kt:16: `"%" + escaped + "%"`) a leading-wildcard pattern — the optimiser can never use these four indices; every search is a scan regardless. Meanwhile each index taxes every INSERT/UPDATE on hot tables: `playback_history` is updated every 5 s during playback (`updatePosition`) — though that touches `lastPositionMs` only, so the title/subtitle indices are not rewritten on the position tick (SQLite only updates indices whose columns change); they ARE rewritten on `updateDisplayByUri`/`updateArtworkByUri`/insert/trim-delete paths.
- Cost is small (tables are 20-row-capped for history; offline_copy tens of rows; enrichment_cache maybe hundreds) → MED not HIGH. Options: drop the four indices (schema bump) or leave as harmless. Given the tables are tiny, the honest engineering call is: dropping them buys ~nothing; keeping them costs ~nothing. Recommend: fold the drop into the next unavoidable schema bump, not a dedicated migration.
- Interdependence: any FTS upgrade for #16 would replace this wholesale.
- Preservation: (a) dropping unused-by-planner indices cannot change results; (b) MIGRATION_20_21 comments show they were added deliberately for #16 — the FEATURE (search) works without them, they simply never engage; (c) cannot recur if a comment records "LIKE '%x%' cannot use B-tree indices". LOW-priority CHANGE-SAFE; do not ship a standalone migration for it.

## data/preferences/SettingsDataStore.kt (~1680 lines, ~120 exposed flows)

### [HIGH] B5-12 — Every exposed flow is a bare `data.map {}` with no `distinctUntilChanged()`; every DataStore write fans out to EVERY live collector
- File: whole class; representative lines 472-519 (8 auto-hide flows), 1464-1491 (19 one-liner flows), consumer `ui/settings/SettingsViewModel.kt:168+` (`combine(listOf<Flow<Any>>(…77+ flows…))`).
- Reasoning: Preferences DataStore emits the ENTIRE `Preferences` snapshot on every `edit`, whatever key changed. A bare `.map { it[KEY] ?: default }` therefore re-emits its (usually identical) value to its collector on every write of ANY key. Consumers that matter:
  - The Settings uiState `combine` of 77+ of these flows: one write (e.g. the user drags the volume-boost slider, or `setLastWasPlaying` fires at app-stop) → 77 upstream emissions → 77 combine re-evaluations → 77-element array copy + full `SettingsUiState` construction each time. Sliders writing per-gesture-step multiply this.
  - Playback-side collectors (PlaybackService combines settings flows with overrides via `withOverride*` — those DO have `distinctUntilChanged`, but only AFTER the combine, so the combine transform itself still runs per write).
  - `scheduledAlarms`, `tagOverrides`, `speedOverrides`, `driveFavourite*` flows re-run their parse + sort (`sortedBy { it.name.lowercase() }` allocates a String per element per compare) on every unrelated write.
  - StateFlow at the end dedupes the FINAL equal value, so no recomposition storm — this is pure CPU/allocation churn, not UI churn. Hence HIGH-for-CPU, not CRITICAL.
- Minimal fix: append `.distinctUntilChanged()` inside SettingsDataStore to each exposed flow (or a private helper `fun <T> pref(key, default) = data.map{...}.distinctUntilChanged()` — also deletes ~300 lines of boilerplate). Parsing flows (sets → sorted lists) should distinct on the RAW set before parsing: `data.map { it[KEY] }.distinctUntilChanged().map { parse(it) }` so the sort/parse only runs when the set actually changed.
- Interdependence: SettingsViewModel's indexed combine (comment at :1369-1371: legacy flows "retained ONLY so the large uiState combine stays index-stable") — adding distinctUntilChanged does NOT change flow order/index, safe. PlaybackService/PlayerViewModel collectors get strictly fewer emissions with equal values — safe by definition of distinctUntilChanged EXCEPT for any consumer using a settings emission as an EVENT trigger (re-fire on write of same value). Sweep required before applying: grep collectors of these flows for side-effects that must run on re-write-of-same-value (e.g. "re-apply EQ preset when user re-taps same preset"). That is the one behavioural hazard.
- Preservation: (a) value-identical stream, fewer duplicates; (b) prior bugs in this file are about encoding (U+001F separators — verified real 0x1F bytes at :1240/:1494, not empty strings) and index-stability of the big combine, neither affected; (c) hazard (b) cannot recur since neither ordering nor encoding changes. CHANGE-SAFE after the event-semantics sweep.

### [HIGH] B5-16 — OAuth-path drive_* cache downloads NEVER run the LRU trim; unbounded cacheDir growth (the exact bug audit 5.11 fixed — but only on the SAF side)
- File: `DriveOAuthProvider.kt:482-543` vs `GoogleDriveProvider.kt:399-402,569-580`.

An OAuth-Drive browse/enrich binge (per item: up to 32 MB head + 32 MB tail; full downloads up to 4 GB) accumulates with only OS storage pressure reclaiming it. - Interdependence: B5-17 (enricher temp deletion) reduces steady-state leakage but not concurrent-peak or crash-leak cases; OfflineMediaManager.relocate deliberately MOVES full files OUT of cacheDir (durable-filesDir fix), so trimming cannot touch durable offline copies — none live there any more.

CHANGE-SAFE.

### [MED] B5-17 — DriveTagEnricher temp files are deleted on the happy path but leak on coroutine cancellation
- File: `DriveTagEnricher.kt:141-160` (head + full temps); contrast `:253-255` (tailArtFallback correctly uses try/finally).
- Reasoning: `runCatching { temp.delete() }` sits AFTER `parseAndApply(...)` as straight-line code, not in a finally. `parseAndApply` is suspend (Room writes, ChapterCache) — if the caller's scope is cancelled mid-parse, CancellationException propagates and the delete never runs. Leaked artefacts: `drive_<hash>_head` (≤32 MB) or `drive_<hash>_full` (≤4 GB) per occurrence. SAF path: next download's trim reclaims; OAuth path: nothing does (B5-16). Additionally `catch (_: Throwable) { null }` around the two download calls (:144, :155) swallows CancellationException, so a cancelled enrich marches through every fallback branch (head → full → tailArt) doing pointless immediately-cancelled work.
- Fix shape: `val temp = ...; try { parseAndApply(...) } finally { runCatching { temp.delete() } }` for both windows; narrow the Throwable catches to rethrow CancellationException (mirror fetchLyricsAsync at SpotifyProvider.kt:1556-1557, which does this correctly).
- Interdependence: B5-16 is the backstop; the existing outer `finally { unmarkFilling }` already releases the dedup flag on cancel — unchanged.
- Preservation: (a) deleting the enricher's OWN temp on all exits is the documented intent (MEMORY: "DriveTagEnricher temp drive_<hash>_full which it deletes"); nothing reads these files after parse; (b) prior bug here was the enricher's delete KILLING a cacheDir-stored offline copy of the same name — already fixed by moving offline copies to filesDir; a finally does not widen WHAT is deleted, only WHEN; (c) cannot recur: same filename space, same single deletion site. CHANGE-SAFE.
