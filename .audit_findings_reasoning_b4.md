# Audit findings — Lens 1 (pure reasoning), Batch B4
Scope: service/, playback/, audio/, widget/, cast/, di/, MainActivity, PowerMediaPlayerApp.
Read-only. Severity: CRIT/HIGH/MED/LOW/INFO. Each change candidate carries a preservation pre-annotation (a: why safe, b: prior bug defended, c: recurrence). Absent that, KEEP-DO-NOT-TOUCH.

## service/PlaybackService.kt (3975 lines)

### [MED] B4-PS-1 — WAKE_MODE_LOCAL under-locks network sources
- PlaybackService.kt:1273 — `setWakeMode(C.WAKE_MODE_LOCAL)` holds only a partial wakelock, no WifiLock. The app streams Drive (`https://googleapis.com`) and podcast HTTP sources through this same player; on screen-off long streams, Wi-Fi doze can stall buffering.
- Reasoning: Media3 `WAKE_MODE_NETWORK` adds a WifiLock; unconditional NETWORK raises battery on local playback (the common case). `ExoPlayer.setWakeMode` is runtime-mutable — the correct minimal change is to flip mode per current item scheme (http/https → NETWORK, else LOCAL) from the existing onMediaItemTransition listener.
- Interdependence: none of the crossfade/cast machinery reads wake mode. Cast playback bypasses local wake needs entirely (CastPlayer).
- Preservation: (a) safe — pure additive switch, LOCAL retained for local files; (b) no prior-bug comment on this line; (c) a stall regression can't recur since LOCAL remains the default. CHANGE-CANDIDATE.

### [MED] B4-PS-2 — subtitleDelayMs collector re-prepares per slider tick (no debounce)
- PlaybackService.kt:1033–1054 — each distinct subtitleDelayMs value triggers `setMediaItem(current, pos)` = full re-extraction. The sibling castVideoAudioOffsetMs collector (994) got `.debounce(350)` precisely because per-drag-tick seeks "flooded the local player". Same hazard here: a slider drag = N re-preparations (decoder re-init, subtitle re-parse each).
- Interdependence: flag write (`subtitleDelayMsFlag`, read at parse time) must stay immediate; only the re-prepare needs the debounce — exactly the split already proven on the cast-offset collector.
- Preservation: (a) safe — same pattern as line 994's fix, flag latency unchanged; (b) defends the documented "seek flood" bug class; (c) can't recur — debounce is the fix for it. CHANGE-CANDIDATE. (Verify UI slider isn't already debouncing writes upstream before crediting a win.)

### [MED] B4-PS-3 — applyCrossfadeTick does per-tick string work at 10 Hz
- PlaybackService.kt:2469–2476 — with album-mode on and crossfade active, every 100 ms tick calls `currentMediaItem.mediaMetadata.albumTitle?.toString()` + `getMediaItemAt(nextIdx)...toString()` and compares strings. Two CharSequence→String allocations + item lookups × 10/s for the whole playing session (tick is correctly event-gated to playing+ms>0 — audit 3.5 — but this cost is inside the active window).
- Fix shape: compute `sameAlbumAsNext` once per onMediaItemTransition/onTimelineChanged (both listeners already exist in this file) into a @Volatile boolean; tick reads the boolean.
- Interdependence: shuffle/queue edits change "next" — the timeline listener covers that; crossfadeAlbumModeFlag flips live — keep the flag check in the tick (cheap) and only cache the string comparison.
- Preservation: (a) safe — same value, computed on the events that can change it; (b) §B2 album mode has no bug-fix comment tied to per-tick recompute; (c) event coverage (transition + timeline) is exhaustive for queue identity. CHANGE-CANDIDATE.

### [MED] B4-PS-4 — §B3 "metadata handoff" block is inert code
- PlaybackService.kt:2542–2554 — on crossfade start it calls `mediaSession?.setSessionActivity(mediaSession?.sessionActivity ...)` — re-setting the *same* session activity is a no-op; no metadata is actually flipped to the incoming track. The comment promises notification/lockscreen handoff that does not occur.
- Interdependence: `started == true` also gates nothing else; `CrossfadeController.maybeStartCrossfade` return value would become unused if removed — keep the call, drop the dead body or implement the real handoff (product decision).
- Preservation: (a) removal is behaviour-neutral (provably no-op: setter receives its own current value); (b) no prior bug — this is an unfinished feature stub, not a fix; (c) n/a. CHANGE-CANDIDATE (flag to owner: either delete or finish; deleting saves a runCatching + getMediaItemAt per crossfade start).

### [MED] B4-PS-5 — companion sender caches survive service destroy (process-lifetime artwork bytes)
- PlaybackService.kt:518–551, 3315–3365 — `senderMetadataByMediaId` / `senderItemByMediaId` are companion (process-static). `pruneSenderCaches` treats an empty liveIds set as "keep everything", and onDestroy never clears them — after a swipe-stop the last queue's artworkData (100 KB–2 MB per track) stays on the heap until process death.
- Interdependence: PlaybackConnection's ghost/flash fallbacks (lastKnownMediaId → cache) only matter while a controller session is alive; after service destroy the SessionSurface empty-state path resets the UI anyway. BUT the caches also serve the mid-cast process-restart reattach (comment at 2611) — that path repopulates from CastPlayer, so a clear on destroy is safe.
- Preservation: (a) clearing in onDestroy only discards data whose consumers are being torn down; (b) the caches defend cast-artwork-echo + cleartext-URI-restore bugs — both are per-live-session concerns, keyed to a live player; (c) those bugs cannot recur from an onDestroy clear because a new session always re-registers items via switchPlayer/onAddMediaItems before casting. CHANGE-CANDIDATE (add `senderMetadataByMediaId.clear(); senderItemByMediaId.clear()` in onDestroy).

### [MED] B4-PS-6 — focus abandon/re-request churn on buffering flips
- PlaybackService.kt:1395–1410 — `onIsPlayingChanged(false)` with `!pausedDueToFocus` abandons audio focus; a mid-track rebuffer (isPlaying false→true, playWhenReady stays true) therefore abandons + re-requests focus per underrun, and opens a window where another app can take focus without us receiving LOSS.
- Reasoning: gate the abandon on `playWhenReady == false` (i.e. a real stop/pause intent) — buffering keeps playWhenReady true.
- Interdependence: this block IS the "call-pause fix" (own focus while playing so a call's transient loss reaches the listener). Changing the abandon condition preserves that: focus still held during playback, still abandoned on genuine pause.
- Preservation: (a) safe if gated on playWhenReady, which is unaffected by buffering; (b) defends the documented call-pause bug (focus requested once at creation never saw LOSS); (c) recurrence impossible — request-on-play is untouched. CHANGE-CANDIDATE, but LOW confidence without a device log showing underrun-driven churn → recommend evidence first (no-guesswork policy).

## service/CastRelayServer.kt (447 lines)

### [HIGH] B4-CR-1 — FaststartDrive heads accumulate in `items` for the whole cast session
- CastRelayServer.kt:50–51, 100–107, 361–364 — every `register()` adds a token that is never removed until `stop()`/`clear()`; a `FaststartDrive` item retains `head.bytes` = ftyp+patched moov, ~19 MB typical, up to the 48 MB cap (MAX_FASTSTART_MOOV, line 60). Casting several audiobooks in one session (or re-picking the same book — each re-cast registers a NEW token, line 101 counter) accretes N×~19–48 MB on the heap until the relay stops. Two book switches ≈ 40–60 MB retained; worst-case OOM pressure on low-RAM devices.
- Interdependence: PlaybackService.stopCastRelay only fires on switch-back-to-local; `clear()` exists but has no callers in this batch's files. Token permanence is deliberate resilience: the CHM comment (48) documents spurious-404 → receiver-error flakiness, and a receiver may retry an older token URL mid-swap.
- Preservation-annotated fix: on `register(FaststartDrive)` evict prior FaststartDrive entries for the SAME fileId (identical content — a retry against the old token for the same file can be served by re-register or a 404-retry the receiver already tolerates for stale queues), or null out `head` on evicted entries while keeping the token mapped to a DriveOAuth passthrough (zero-404 guarantee preserved, memory released). (a) Safe under the passthrough-downgrade variant — old URLs keep working, just un-optimised; (b) defends the 404-flakiness bug by NOT removing tokens; (c) recurrence impossible since tokens stay mapped. CHANGE-CANDIDATE (passthrough-downgrade variant preferred).

### [LOW] B4-CR-2 — `@Synchronized register/clear` over a ConcurrentHashMap + AtomicLong
- Lines 99–112 — the sync adds nothing (both structures are thread-safe; no compound invariant spans them). Harmless; removing is cosmetic. KEEP unless touched.

### [INFO] B4-CR-3 — buffer/stream handling verified good
- Seekable-fd lseek path with stream fallback (140–223) names the 20–30 s cast-start bug it fixed; fd-leak guards on both close paths; 206-only guard in driveRangeBytes (389) prevents the multi-GB OOM; prepExecutor shutdownNow on stop. KEEP-DO-NOT-TOUCH.
